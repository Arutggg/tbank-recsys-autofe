# Runbook: как прогнать всю работу самому

Порядок запуска, время каждого шага и что должно получиться. Все числа
в отчёте получены ровно этими командами.

Машина, на которой всё замерялось: MacBook Air M2, 8 ядер, 16 ГБ RAM,
без GPU. Времена ниже — для неё.

---

## 0. Окружение (один раз, ~3 мин)

```bash
brew install libomp          # LightGBM на macOS без этого не импортируется
make setup
make test                    # 24 теста, ~3 с
```

Тесты должны пройти все. Два из них — ключевые:

- `test_no_leak_future_events_do_not_change_features` — признаки не меняются,
  если дописать в лог будущие события;
- `test_leak_detector_actually_detects_leak` — позитивный контроль: тест
  выше действительно способен поймать утечку.

## 3. Что важно понимать при защите

Четыре результата, и три из них **против** первоначальной гипотезы.
Именно они определили конструкцию, и именно их стоит уметь объяснить.

**1. Почему отказались от приближения окон экспонентами.**
Индикатор окна `1[s<W]` разрывен в точке `s=W`. Сумма гладких экспонент
разрыв не воспроизводит: sup-ошибка остаётся ≈0.52 при любом числе ядер
(проверено от K=2 до K=32). Восстановление окна из базиса затуханий — это
обратная задача Лапласа, она плохо обусловлена: `‖c‖₁` доходит до 3.6·10⁵,
и на уровне самого признака `R² ≈ −10⁸`. Вывод: окно и затухающий счётчик
— разные функционалы истории, теоретически их не сравнить, только
экспериментом.

**2. Почему примитив — моменты возрастов, а не счётчики.**
Окно — это один срез распределения возрастов событий. Вместо срезов берём
моменты этого распределения. Все три поддерживаются за O(1):
`A → e^{-λΔ}A`, `B → e^{-λΔ}(B+ΔA)`, `C → e^{-λΔ}(C+2ΔB+Δ²A)`.
Проверено против определения с точностью 1e-16.

**3. Почему отбор модели по log-loss, а не по AUC.**
Признаки с полупериодами 0.6 дня и 12 дней дают одинаковый AUC до
четвёртого знака (0.7424), хотя содержат разное количество информации
(57% нулей против 38%). AUC ранговый и насыщается. На полигоне с известным
оптимумом log-loss находит истину, AUC промахивается в 8 раз.

**4. Почему смешанный протокол негативов.**
На RetailRocket при негативах по популярности **один бинарный признак**
«видел ли юзер этот айтем» даёт NDCG@10 = 0.9095, потому что лишь 1.4%
негативов вообще встречались пользователю. Любое число около 0.9 на таком
протоколе ничего не говорит о модели. В проде кандидаты приходят от
ретривера и все правдоподобны, поэтому негативы собираются как у
ретривера: история 40%, та же категория 30%, популярность 30%.

**5. Какая утечка была найдена и исправлена в собственном коде.**
Свойства айтема в RetailRocket временные. Джойн «последнее известное
значение» даёт покрытие категории 96.6% против 79.7% у корректного as-of —
17 пунктов чистой информации из будущего. Эта утечка не ловится обычной
проверкой агрегатов, потому что сидит в джойне атрибутов. В `build_queries`
она была, нашлась и исправлена, тест добавлен.

## 4. Если что-то упало

| симптом | причина | что делать |
|---|---|---|
| `OSError: libomp.dylib` при импорте lightgbm | на macOS нет libomp | `brew install libomp` |
| `ModuleNotFoundError: pkg_resources` | setuptools ≥81 выкинул его | `pip install "setuptools<81"` |
| `не найден data/retailrocket/events.csv` | данные не скачаны | `make data` |
| нехватка памяти на `make e03` | 1944 признака × много строк | уменьшить `--n-positives-train` |
| `numba` компилируется долго при первом запуске | JIT-компиляция | нормально, со второго раза кэш |
